# D078 Progressive-Behaviour Implementation Gap Audit

**Date:** 2026-10-31  
**Scope:** Progressive selection and reveal from Social Sciences domain foundations through methods/designs, domain items, areas, area items/task families, roles, role items and tools.  
**Out of scope for this audit:** End-to-end test-pack authoring, analytics, report redesign and unrelated tray work. The vacancy/role-discovery requirement is recorded at the end so it is not lost.

## Decision

The progressive selection and reveal behaviors in scope are **implemented locally**. The UI presents unordered learning as choices, narrows area contributions and role task narratives to explicit work focus, supports graph-backed alternative comparison while allowing both choices to remain selected, and preserves saved route state. Focused regression tests and the web build pass. Authenticated rendered browser acceptance remains unverified because the browser access host is unavailable in this environment; this is a verification limitation, not an outstanding implementation item.

The progressive-behaviour implementation pass is closed locally. The vacancy-to-role report requirement is a later report/product task, not part of this repair.

## User-requested behaviour this audit checks

1. A learner sees the three domain foundations and the pre-method society/domain orientation before choosing a method.
2. Choosing one method focuses the picker on that method, while retaining a clear way to reveal another compatible method. A multi-method choice must resolve to an exact, reviewed named design; it must never union unrelated method routes.
3. A selected named design replaces its component-method picker view and controls the downstream area, item, tool and role route. Participatory designs may expose one or more supported evidence methods progressively.
4. Layer 2/3 preparation appears only when supported by the chosen method/design, with its condition and optional/needed status preserved.
5. Selecting a domain, area, task-family, role or learning item should focus the experience on its supported next choices; deselection should restore the prior choices. Methods, areas, task families and learning items may be multi-selected only where the graph supports that combination.
6. Items are grouped by requirement/usefulness, not by item kind. Their ordering and alternatives must follow the approved graph relationships. Tools must stay connected to their task/method context.
7. Selection changes should reveal/hide the next context with a clear transition, without implying that a useful edge is compulsory.

## Why learning order matters

An alphabetical list does not corrupt the content or create a false prerequisite by itself, but it can look like a learning sequence. The current helper preserves graph-supplied route order without treating it as instructional order, and the area/role lanes label these items as choices rather than ordered steps. The interface should use graph-backed sequence order only where the graph has a reviewed sequence contract. Where it does not, it should present choices and avoid implying a teaching order. Do not manufacture a prerequisite to impose an order.

## Closure status

1. Learning items with no reviewed sequence contract are presented as choices. Task-family membership, role-item visibility and `builds_on` do not imply compulsory order.
2. Other compatible choices can be revealed, and graph-marked alternatives can be compared at domain, area and role stages. Both endpoints remain selectable unless an explicit reviewed mutual-exclusion rule exists.
3. Area items, contribution cards, associated tool candidates and role task narratives follow the selected work focus where a resolved graph link exists. General role learning items remain available because no reviewed task-family-to-role-item link exists; the UI explains that boundary.
4. Selection transitions, reduced-motion behavior, announcements, add/remove, alternatives, compatible multi-selection, Undo, and saved-route restoration have local regression coverage. No remaining local implementation item is identified by this audit.
5. Authenticated browser acceptance is the sole open verification gate. The browser access host was unavailable during this pass. Re-run rendered acceptance when that environment is available; do not describe it as passed based on component tests.

## Carry-forward: vacancies and roles beyond the database

The final learner report must not be limited to the roles already listed in the database. A future vacancy-matching/report feature should let a learner paste a job description or vacancy text and compare its stated duties and requirements with the learner’s selected domain, area, method and items. It should separate **direct matches**, **transferable/related capabilities**, and **requirements not demonstrated by this route**, with a confidence/evidence explanation. The wording must say that the learning route may help the person pursue or assess the vacancy; it must not claim guaranteed eligibility or job readiness without the employer’s actual requirements. This is a deferred report/product requirement, not part of the progressive-reveal repair gate.
