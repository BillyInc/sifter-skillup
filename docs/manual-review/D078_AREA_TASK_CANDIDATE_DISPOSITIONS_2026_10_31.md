# D078 Unrouted Area-Task Candidate Dispositions

**Date:** 2026-10-31  
**Purpose:** Resolve the 16 area-task-family nodes that were present in the graph but absent from every method/design route. This is a disposition register, not a student-release approval or SQL migration.

## Decision rules

- A candidate is not a student route merely because its title sounds relevant. It must connect to an exact domain/method/design choice, its owned area learning, and (where applicable) the role-task context.
- Duplicate wording is merged into the canonical family or item; it does not create a second selectable card.
- A distinct task family is retained only when it represents different work, has a source-supported route trigger, and has exact owned learning links.
- Area foundations that apply before task-family choices are recorded as foundations, not disguised as another task-family choice.
- Emerging/AI-assisted work remains optional and bounded. It never becomes a universal requirement or a progression blocker.

## Sequencing contract that follows these dispositions

1. Carry the programme and the learner’s selected domain foundations/options into the selected method or named design.
2. Rank available areas by exact selected-route fit and selected domain-context evidence. Keep all supported areas available; the rank is a recommendation, not an admission or progression gate.
3. On an area route, show any approved area-wide foundation first (including bounded question framing where it applies), then reveal only task families supported by that exact method/design and selected domain context.
4. Task families are parallel work-context choices unless an explicit, reviewed dependency says otherwise. Within each family, show only its own item links, alternatives and conditional AI/tool extensions; do not merge sibling-family item sets.
5. Show roles only within the selected area and supported route. Rank roles by selected family/task-context match first, then by route fit. This is a navigation recommendation, not a job-readiness claim.
6. At a role, show source-backed role-task context, then role-owned items in their requirement lanes. No role-item ordering is inferred from alphabetic order, source-file order or item type. A role item becomes a predecessor only if a typed, item-specific, reviewed dependency is evidenced.

The graph currently has eight approved area-sequence edges (three conditional prerequisites and five non-blocking workflow recommendations). The 22 other area-order declarations are explicitly non-sequence dispositions. The current role contract has 161 route-eligible role items and zero approved role-item dependency edges; therefore the correct role-item behavior is parallel, skippable choices by requirement lane, not a fabricated linear order. These rules preserve the no-option route and every valid optional selection subset.
