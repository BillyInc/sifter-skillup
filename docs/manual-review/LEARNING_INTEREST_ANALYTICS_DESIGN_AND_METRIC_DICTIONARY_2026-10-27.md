# Learning-interest analytics: design and metric dictionary

**Status:** Local implementation contract; migrations have not been applied to Supabase.  
**Purpose:** Help LevelUp product owners and participating schools understand what learners explicitly choose, so learning materials and routes can be prioritized using observed interest.

## Audiences and access

- The product team uses `/analytics` for platform-wide aggregates and filters.
- A verified school owner/admin uses the institution analytics surface for aggregate choices attributed to learners affiliated with the selected school when each choice was recorded. If the admin has several verified memberships, they must choose the institution; the dashboard does not silently pick one.
- A school administrator does not receive an individual learner's route, name, email, grades, or saved plan through analytics. Existing school roster/guidance access remains separately consent- and role-gated.
- Dashboard reads must pass the backend's role checks and use the aggregate database function. Never query or expose raw event rows in a dashboard.

## What is counted

Analytics records an explicit Add, Remove, or separate-route copy only when the learner has opted in. Activity metrics count Add and Remove actions; copying a route contributes its copied choices to the current-selection snapshot but is not treated as fresh learning demand. It does not count impressions, page opens, inferred interests, course completion, or every item merely displayed on screen. Programme and institution choices, domains, areas, roles, methods, named research designs, tools, skills, competencies, knowledge, certifications, and other learning items are separate selectable dimensions. In the D078 method-aware route, choosing/opening an area or role is recorded as a route choice, item toggles in domain/area/role pages update the same active-selection snapshot, and removing an entire route removes its tracked choices; ordinary page views remain uncounted.

Selection remains immediate even if analytics is slow or the learner briefly loses connectivity. A clear network/timeout failure is stored in the existing encrypted, account-and-device-scoped write queue and replayed when connectivity returns; permanent API/setup errors are not retried as if they were offline. The replay uses the original event ID for idempotency, preserves event order, and is subject to the backend's current consent check—so a queued event is not permission to bypass later consent withdrawal.

| Measure | Definition | Interpretation |
|---|---|---|
| Learners who added a choice | Distinct opted-in accounts with at least one `selection_added` event in the selected time window, after the active filters | People who expressed interest by adding something during this period; not a count of currently saved selections |
| Learners who removed a choice | Distinct opted-in accounts with at least one `selection_removed` event in the selected time window, after the active filters | People who edited or removed a choice during this period; separate from the number of remove actions |
| Learners with choices selected now | Distinct opted-in accounts with an active item selection in the current-selection snapshot, after the active filters | Current expressed interest, independent of the date window; not a completion or saved-path count |
| Add actions | Number of explicit additions during the window | Measures selection activity; repeated add/remove cycles can increase it |
| Remove actions | Number of explicit removals during the window | Indicates changes of mind or route editing; it is not a negative learner count |
| Learners per item, current | Distinct accounts that currently have that exact item selected in one or more active route scopes | Current-intent signal for prioritizing a tool, method, programme, domain, area, role, or other item |
| Learners per item, recent | Distinct accounts that added that exact item in the window | Recent activity signal; separate from current intent |
| Active route contexts | Distinct active route-scope keys across all current selections, after active filters | Counts separate learner/route scopes with at least one current choice; does not count route patterns or prove the learner saved/completed the full route. |
| Current labeled route patterns | Distinct route-context hashes with a non-empty route label among current active selections, after active filters | Counts different labeled combinations of route context currently represented, regardless of how many learners or route scopes share each pattern. Unlabeled scopes still count in active route contexts but are not guessed into named patterns. |
| Recent labeled route patterns | Distinct route-context hashes with a non-empty route label attached to at least one Add event in the selected window, after active filters | Counts different labeled route patterns in recent additions, not individual selection scopes. The dashboard lists up to 50 patterns with learner and add totals. |
| Daily additions and removals | Explicit add and remove actions grouped by UTC event day | Selection edits over time, not study progress or completion |
| Contexts | Distinct route-context hashes attached to events for an item | Indicates how broadly the item appears across selected routes |
| Previous-period comparison | Learners-who-added and add/remove measures over the immediately preceding interval of equal duration, using the same filters | Like-for-like recorded activity comparison; not a forecast or current saved-intent count |

Counts are exact, including small groups, as explicitly requested by the product owner. They are available only to the authorized product team or verified institution audience and remain aggregate-only; however, a count of one in a small school cohort can make a learner's choice inferable to someone who already knows the cohort. This limitation is disclosed in the privacy and terms copy. Do not add a minimum-cell suppression gate without a product decision and corresponding policy/version update.

## Filters and interpretation

The dashboard supports a 7/30/90/365-day window and choice type. Route-context filters use a searchable picker backed by consented event labels, so staff can search names such as Sociology, Social Sciences, Python, undergraduate, or a named Sociology-to-method route instead of needing internal IDs. Results show the dimension and aggregate learner count, can be combined across dimensions, and can be removed individually. Programme and domain are first-class filters; methods, designs, tools, other typed learning items, named route patterns, learner stage, event-time school state, and event-time affiliated school are searchable too. One exact learning-item or named route-pattern filter can be active at a time because the aggregate API accepts one exact item-type/ID pair; it can still be combined with programme, domain, institution, stage, state, and affiliated school. This lets staff inspect a route pattern beyond the 50-row route preview and see the choices associated with that route. “Institution” is the university or centre explored in the route; “affiliated school” is where the learner was affiliated when the choice was recorded. Keep these separate. The backend derives options only from the caller's authorized platform or school scope and selected time window. School state and school IDs are snapshotted with the event; later affiliation changes do not rewrite the historical cohort or state. University context is stored as its own selected-institution dimension and is never used as a proxy for the learner's location.

The entity list is ranked first by distinct learners who currently have the choice selected, then by distinct learners who added it in the selected window. Current selected learners and active route scopes are separate from period additions/removals and route patterns. Current counts do not use the date-window limit; activity counts do. The dashboard shows up to 50 current labeled route patterns with the number of learners and active route scopes represented, separately from up to 50 recent labeled route patterns with learner and Add totals. Unlabeled active scopes remain included in the active-context total but are not guessed into a named pattern. A pattern is not an individual scope and neither measure proves that a full route was saved or completed. Current route metadata is refreshed across the remaining items in a selection scope when a new add/remove event arrives, so an active context reflects the latest known selection state. The learner stage and school/state affiliation remain those snapshotted when each individual choice was made; route refreshes do not rewrite cohort attribution. The API returns at most 100 ranked choice rows; route totals are computed independently. Searchable filters include entities found in current selections as well as recent event history. These analytics snapshots are not the learner's operational saved plan; My World and reports continue to use their own path data.

When a learner explicitly creates a separate D078 route by copying the active route, the copied choices are recorded as `selection_copied`: they populate the new route's current-selection context but do not inflate add-action or recent-addition metrics. Removing a copied choice affects only that route scope; the same choice remains active in other routes until removed there too.

CSV export contains audience scope, exact activity-window start/end (end exclusive), selected choice type and context filters, generation time, current-selection totals and item counts, the displayed event summary, equal-duration previous-period comparison, current and recent route contexts, and daily activity. Text cells are quoted and escaped; formula-like labels (including leading whitespace and full-width formula markers) receive a leading tab for Excel-safe human viewing. That tab remains part of the value and may affect machine re-import, so this export is not a machine interchange format. It is aggregate data and must never contain account IDs or direct identifiers.

## Consent, security, and retention

- Analytics consent is separate from account creation and saved-plan functionality; no event or active snapshot is written for users who have not opted in.
- Analytics capture requires consent attached to the current Terms and Privacy versions. The current-selection table is cleared when consent is withdrawn or must be renewed; fresh consent begins a new snapshot from subsequent explicit choices.
- The client queues selection events in action order within each route scope so a quick add-then-remove is not applied to the current snapshot backwards. D078 transitions and tray removals must use the same route-scope identifier for both additions and removals. Capture remains best-effort and never blocks the selection UI; this ordering guarantee is within one running client, not across simultaneous devices.
- Event rows retain a protected user link solely for account lifecycle/correction/deletion operations and event deduplication. Dashboard viewers cannot query that link.
- `user_id` cascades on account deletion. A Supabase Cron job deletes raw events after 395 days; the query window is capped at 365 days. Active selections persist only while consent remains current and the learner keeps the choice selected.
- RLS is enabled and raw table privileges are restricted to `service_role`. The backend authorizes audiences before calling the aggregate-only `SECURITY DEFINER` function.
- Exact small-group aggregates are a deliberate product choice, not a claim that such counts are anonymous in every context. Handle exports and access with the same audience/purpose limits as the dashboard.

## Dashboard layout contract

1. Put audience/scope, last-updated time, and reporting-window controls first.
2. Put current intent and activity side by side: learners with choices selected now (unwindowed), followed by unique learners who added/removed and add/remove actions for the chosen time window. Compare only windowed activity measures with the immediately preceding equal-duration period.
   State beside the summary measures that a zero means no matching opted-in choices were recorded, not proof that no learners are interested; this dashboard has no validated eligible-user denominator and must not imply a participation rate.
3. Put choice-type and searchable, human-readable route-context filters before the ranked item table; never require staff to know internal record IDs.
   When a filter changes within the same audience/institution scope, keep the active filters, search control and current results on screen while the new aggregate loads; show a small refresh status instead of replacing the dashboard with a blocking spinner. If the refresh fails, retain the last successful results, label them as stale, and offer retry; never make old results look current under newly selected filters. If several requests overlap, only the response for the latest filter state may replace the displayed data. When a school admin changes institution scope, clear the previous institution's aggregates immediately so they cannot appear under the newly selected school while its request loads.
4. Show choices ranked by current selected learners first, then recent activity, with explicit current learners, active route scopes, recent learners, add/remove and labeled route-pattern columns. Show current labeled route patterns (with the learners and active scopes represented) separately from recent labeled route patterns (with learners and Add totals), plus a daily/weekly/monthly adds-and-removes chart. Put equal-duration previous-period comparisons only on windowed measures and include their exact date interval in the aggregate CSV.
5. Include definitions that distinguish current selection, recent activity, saved plans and completion. On narrow screens, render ranked choices as stacked cards instead of squeezing the desktop table. Summarize chart buckets weekly/monthly for longer windows while retaining daily rows in CSV. Do not use color alone; keep labels, keyboard/screen-reader access, readable contrast, and usable narrow-screen layout.
6. Offer CSV export of the aggregate result shown, not raw event data. The activity series uses UTC dates and includes zero-activity days so quiet periods remain visible and weekly/monthly buckets preserve the timeline.

This layout follows Microsoft's dashboard guidance to foreground decision-relevant measures, give each visual context, keep comparisons readable, and design for the audience. The searchable selection chips follow Microsoft's slicer guidance to make current filters visible and searchable rather than forcing users to remember internal identifiers. Accessibility guidance calls for keyboard/screen-reader support, contrast, labels, and not relying on color alone.

The interaction and visual hierarchy were also checked against Tableau's official dashboard guidance: guide the reader through a logical sequence, use clear titles/subtitles to explain what controls do, make interactions discoverable, and keep the view focused rather than crowded. The dashboard applies this through an explicit audience/scope heading, explanatory filter labels, visible active-filter chips with individual removal, and separate panels for current choices, current routes, recent route contexts, and time-series activity. Each time-series bucket is an accessible chart item named with its date and both addition/removal counts; a text legend repeats the series meanings so color is not the only cue. It does not add cross-highlighting or hover-only information because this dashboard's data is rendered in an accessible table/card form and the filters already provide the needed analysis path.

## Remaining verification gates before calling the product complete

- Both Supabase migrations and the retention job are prepared locally but not deployed; live persistence is unverified until the user applies migration #20 then #21 and passes the runbook postflight.
- If an analytics aggregate or filter RPC reports a known missing-function/table/column schema code, the API returns an actionable `503` setup message instead of the global generic `500`; unrelated provider/permission errors retain their normal handling.
- The active-selection snapshot has no historical backfill by design. Current counts start when the new migration and consented instrumentation are active; do not infer current intent from old event history or unconsented saved paths.
- Searchable, human-readable filters are implemented locally and covered by UI/API tests; the live SQL function and its authorization-scoped option search remain unverified until the migration is applied and tested against Supabase.
- Opt-in participation rate is not provided because there is no validated eligible-user denominator. Equal-duration event-activity comparison compares the selected window to the immediately preceding interval with identical filters and must not be described as current intent or learner growth.
- The school cohort event-time snapshot and affiliated-school filter are implemented in the SQL contract but need a database-backed post-apply test proving affiliation changes do not move old choices between schools and platform-level school segmentation cannot widen the school-admin authorization boundary.
