2. The Complement Map: "What does this skill need to become sellable?"
This is the sharper insight, and yes — almost no skill monetizes alone. Every monetization path is really a bundle of skills, and the skill you have is usually just the "core." The rest are complements, and they fall into predictable categories:

Technical complements — adjacent hard skills (welding + reading blueprints)

Business complements — pricing, invoicing, contracts, licensing

Sales/marketing complements — finding customers, positioning, outreach

Operational complements — scheduling, supply chain, insurance, tooling

People complements — hiring, managing, delegating

Financial complements — cash flow, taxes, capital

Legal/regulatory complements — permits, certifications, liability

The key realization: your income is often capped not by your core skill but by your weakest necessary complement. A brilliant welder who can't price or find customers stays broke. A great developer who can't sell stays employed.

3. The learn-vs-partner decision (you nailed this)
For every complement, there are only three real options:

Learn it yourself — best when it's cheap to learn,高频 used, and core to your differentiation

Partner/hire for it — best when it's expensive to learn, rarely used, or someone else is far better

Buy it as a service — best when it's commoditized (accounting, legal, ads)

And the decision rule is roughly:

Learn if it's high-frequency + high-leverage + cheap to acquire.
Partner if it's high-leverage but low-frequency or expensive to master.
Buy if it's low-leverage and commoditized.

The index makes this concrete: for skill X → path Y, it shows the full complement stack, and for each complement, flags whether the typical successful person learned it, partnered for it, or bought it.

How do we derive this mapping from the creations per domain index?
Great question — this is the architectural crux. You're asking: if I already have a "creations per domain" index, how do I derive the skill→domain→mechanism mapping from it, rather than building a second index by hand?

The answer: you don't build two indexes. You build one index with the right schema, and the skill mapping falls out as a query.

Let me show you how.

The Core Insight
A "creation" (business, product, service) is not a standalone thing. It's a bundle:

Creation = Domain × Mechanism × Core Skill × Complement Stack

If you structure every entry in your index this way, then:

Domain → Creation is just a filter on domain

Skill → Domain is just a filter on core_skill or complement_skill

Skill → Mechanism is just a group-by on mechanism

Skill → Cross-domain is just a filter on core_skill without filtering on domain

One index. Multiple views. That's the whole trick.

The Schema (this is the key artifact)
Every creation in your index gets an entry like this:

text
Creation {
  id
  name                    // "Mobile welding for farms"
  domain                  // "Agriculture" (primary)
  cross_domains[]         // ["Construction", "Equipment Repair"]
  mechanism               // "Service" | "Product" | "Teaching" | "Content" | "Employment"
  
  core_skills[]           // ["welding"] — the skill that defines this creation
  complement_skills[]     // ["blueprint reading", "pricing", "customer outreach"]
  
  complements {
    skill
    category              // technical | business | sales | ops | legal | financial
    learn_or_partner      // learn | partner | buy
    why                   // "high-frequency, cheap to learn"
  }
  
  capital_required        // low | medium | high
  entry_point             // "start with 1 client, ₦X tooling"
  scale_path[]            // informal → formal → export
}
Notice: skills are just attributes of a creation. You don't index skills separately. You index creations, and skills become queryable dimensions.

How Each Mapping Derives from the Index
1. Domain → Creation (trivial)
text
SELECT * FROM creations WHERE domain = 'Agriculture'
Output: every business/product/service buildable in agriculture.

2. Skill → Domain (the join you asked about)
text
SELECT DISTINCT domain, cross_domains
FROM creations
WHERE 'video editing' IN core_skills OR 'video editing' IN complement_skills
Output: every domain where video editing creates value — including cross-domains, because you stored cross_domains[].

Step 1: Seed the creations.

Step 2: Tag skills consistently.

Step 3: Normalize mechanisms.

Step 4: Store cross-domains explicitly.

Step 5: Query, don't re-index.
Every view you want — skill→domain, skill→mechanism, domain→creation — is a SQL query on the same table. You never maintain a second index.

Step 6: Let AI fill gaps, then verify.
Use an LLM to propose skills/complements for a creation, then human-verify. This is how you scale from 100 to 10,000 creations without hand-authoring everything.

This is the technical heart of it. You don't derive a guaranteed probability, because that doesn't exist. Instead, you score each path based on observable evidence of demand.

You can build a Monetization Score for every Skill → Domain → Mechanism path using signals like:

Active Demand (Strongest Signal): Are there live job postings or freelance gigs on platforms like Upwork or LinkedIn that ask for this specific skill for this specific task? This is hard evidence that money is already changing hands.

Paying Customer Density: How many actual businesses in that domain routinely hire for this? A domain with thousands of small businesses needing bookkeeping is a higher-probability path than a niche domain with 5 firms.

Problem Intensity: Does this skill solve a "painful problem" (saves money, saves time, increases revenue, reduces risk) or just a "nice-to-have"? People pay more consistently for pain relief.

Skill Scarcity: Is the skill common in that domain, or is it a bottleneck? If every business in a domain is starving for a specific skill, the probability of monetization for someone with that skill goes way up.

This is how you turn a map into a decision engine. You're not promising success. You're showing people the paths where evidence of demand is strongest, so they can place their bet wisely.

How far back should you document creations?
This is the harder question, and there's no single right answer — but there's a defensible principle.

The principle: document back to when the archetype became commercially documented in a verifiable source.

In practice, that means different cutoffs for different archetype types:

Layer 1 (Documented Archetypes) — go back as far as sources allow

Classic archetypes (50+ years): Go back to the earliest commercial documentation you can verify. For independent pharmacy, that's the 19th century or earlier. For farming cooperatives, medieval. For tutoring, ancient.

Established archetypes (10-50 years): Go back to the first documented instance. A management consultancy, a health tech company, a design agency — document the first verifiable commercial entity.

Modern archetypes (last 10 years): These are self-limiting — you document what emerged in the last decade.

The practical cutoff for Layer 1: You don't need to document every archetype back to antiquity. You document archetypes that are still viable today. A business model that existed in 1850 but is obsolete now is not useful to a user building something in 2026. So the question isn't "how old is this archetype?" but "is this archetype still a viable pattern someone could build today?"

If yes, document it — and note its maturity level (Classic/Established/Modern). If no, it's history, not an archetype.

Layer 2 (Emerging Archetypes) — only the last 3-5 years

These are businesses forming now. The window is tight by definition. You're documenting what's forming in the last 3-5 years, with formation stages (PROTO/FORMING/CONSOLIDATING).

Layer 3 (Signals) — current conditions only

Signals are conditions that make something currently possible. They're time-sensitive. A signal from 10 years ago that's already been addressed is inactive. A signal from today is active. The layer is inherently present-tense.

The boundary you should watch
The risk of going too far back: You flood the index with obsolete archetypes. A user sees "Independent Blacksmith" (documented for 500 years) alongside "Digital Pharmacy Platform" and can't tell which is viable. The index becomes a museum, not a tool.

The risk of not going back far enough: You miss archetypes that are old but still hugely viable. Independent pharmacy, family farming, private tutoring, construction contracting — these are centuries old and still dominant in many markets. Excluding them because they're "old" would be wrong.

The resolution: Document the archetype, but let the maturity level (Classic/Established/Modern) and the track type (MICRO/SMALL/SCALABLE/CREATOR) tell the user what they're looking at.
