# D001 — Software Engineering

Global specialization recommendation reconciliation (2026-10-06). This is an internal recommendation, not canonical taxonomy or external academic sign-off.

- **Candidate areas:** 6
- **Evidence URLs:** 4 unique; 4 source records screened as global/international
- **Canonical changes / role assignments:** none / none
- **Geographic scope:** global phase only; Nigerian-specific evidence intentionally deferred

## Recommendation

Replace the excluded ISCO occupational bucket with six curriculum-grounded candidate areas of specialization. Retain platform types as examples within software construction/development rather than creating a separate subgroup for every platform. Keep software security distinct as a recognized software-engineering focus while preserving the boundary with the separate Cybersecurity domain. This recommendation does not reassign or validate any role.

## Candidate areas and boundaries

- **Software Requirements and Modeling.** Elicit, analyze, specify and model stakeholder needs and system behavior so a software solution can be designed against clear requirements.
  - Source claim: SE 2014 identifies requirements analysis/specification and software modeling/analysis; SWEBOK V4 has a dedicated Software Requirements knowledge area.
- **Software Architecture and Design.** Shape software structure, components, interfaces and design decisions to meet functional and quality requirements.
  - Source claim: SE 2014 includes software design; SWEBOK V4 treats Software Architecture and Software Design as distinct knowledge areas, grouped here as one closely related specialization for a concise student taxonomy.
- **Software Construction and Platform Development.** Implement, integrate and maintain software, choosing suitable development approaches for web, mobile, embedded and other target platforms.
  - Source claim: SWEBOK V4 has a dedicated Software Construction area including cross-platform development; CS2023 names Specialized Platform Development and gives web, mobile and embedded as examples.
- **Software Testing, Verification and Quality.** Plan and perform testing and verification, evaluate software against requirements, and improve product quality and reliability.
  - Source claim: SE 2014 separately identifies verification/validation and software quality; SWEBOK V4 has a dedicated Software Testing knowledge area. Quality remains cross-cutting in the curriculum source.
- **Secure Software Engineering.** Build security requirements, threat-aware design, secure implementation and security testing into the software lifecycle.
  - Source claim: SE 2014 includes a security knowledge area; SWEBOK V4 treats Software Security Engineering and Processes as a dedicated area. This is secure software practice, not general cybersecurity governance or incident response.
- **Software Engineering Operations and Reliability.** Release, operate, monitor and improve software systems through configuration, delivery, service reliability and lifecycle maintenance practices.
  - Source claim: IEEE Computer Society SWEBOK V4 identifies Software Engineering Operations as a knowledge area; SE 2014 includes software process and configuration-related concerns. This area concerns software lifecycle operations, not all cloud infrastructure work.

## Source evidence and limits

- [IEEE Computer Society and ACM — Software Engineering 2014: Curriculum Guidelines for Undergraduate Degree Programs in Software Engineering](https://ieeecs-media.computer.org/media/education/reports/SoftwareEngineering_UnderGrad_2014.pdf) — Chapter 4, §4.7, pp. 26–27: SEEK knowledge areas include requirements analysis and specification, software design, software verification and validation, software process, software quality, and security. §4.5, pp. 25–26, cautions that knowledge-area ordering does not prescribe curriculum sequencing and identifies quality/security as cross-cutting concerns. **Supports:** A recognized software-engineering education framework distinguishes core lifecycle and assurance knowledge areas within the parent discipline. **Limit:** These are knowledge areas, not an officially mandated subgroup taxonomy or proof that each should become a separate student-facing specialization. The recommended groupings below are an internal synthesis, not an ACM/IEEE-endorsed taxonomy. **Scope screen:** global_or_international_source.
- [IEEE Computer Society — SWEBOK Guide V4.0 Topics](https://www.computer.org/education/bodies-of-knowledge/software-engineering/topics) — Table of contents: Chapters 1–5 (Software Requirements, Software Architecture, Software Design, Software Construction, Software Testing); Chapter 13 (Software Security); chapter on Software Engineering Operations. The overview states the guide comprises 18 knowledge areas. **Supports:** The professional body of knowledge separately recognizes requirements, architecture, design, construction, testing, security, and engineering operations as substantive areas within software engineering. **Limit:** A body-of-knowledge chapter is not automatically a labor-market occupation, a standalone university specialization, or evidence for assigning a particular role to this domain. **Scope screen:** global_or_international_source.
- [Association for Computing Machinery, IEEE Computer Society, and Association for the Advancement of Artificial Intelligence — Computer Science Curricula 2023](https://csed.acm.org/) — Final Report sections on knowledge areas and competency areas; Specialized Platform Development examples include web, mobile, and embedded platforms, and Software Engineering is a separate knowledge area. **Supports:** Platform work is a recognized curricular dimension and can be represented within a software-development specialization without treating every platform as a separate parent-domain specialization. **Limit:** CS2023 is computer-science curriculum guidance, not a software-engineering subgroup standard; web/mobile/embedded examples do not require separate taxonomy entries. **Scope screen:** global_or_international_source.
- [IEEE Computer Society — SWEBOK Guide V4.0 Topics](https://www.computer.org/education/bodies-of-knowledge/software-engineering) — Table of contents: Chapters 1–5 (Software Requirements, Software Architecture, Software Design, Software Construction, Software Testing); Chapter 13 (Software Security); chapter on Software Engineering Operations. The overview states the guide comprises 18 knowledge areas. **Supports:** The professional body of knowledge separately recognizes requirements, architecture, design, construction, testing, security, and engineering operations as substantive areas within software engineering. **Limit:** A body-of-knowledge chapter is not automatically a labor-market occupation, a standalone university specialization, or evidence for assigning a particular role to this domain. **Scope screen:** global_or_international_source.

## Open limits / reconciliation notes

- The six-area grouping is a transparent internal synthesis of authoritative knowledge taxonomies, not an official ACM, IEEE, ABET or Nigerian accreditation taxonomy.
- SE 2014 explicitly treats software quality and security as cross-cutting; local academic reviewers may prefer them as tags across areas rather than standalone specializations.
- The D001 scope description and its 37 current role mappings include apparent cross-domain occupations; these are deliberately excluded from the specialization-count rationale and require the separate role audit.
- Canonical implementation remains pending because the seed/schema currently key subgroup identity to ISCO submajor. Independent specialization identifiers and a migration/API compatibility plan are required before promotion.

## Audit boundary

No roles were assigned to these areas. Current subgroup counts, ISCO grouping, role frequency and computational keyword hits were not used to determine candidate count. Nigeria-specific context is explicitly out of scope in this global phase.
